Fid Coder Positioning brief · Engineering leadership · 10 November 2026

One-Search finds it.
VS Code edits it.
Fid Coder finishes it.

Fid Coder is the only one of the three that carries context from Jira, GitHub, and the browser into the repo, makes the change, pauses before the irreversible step, and leaves a record you can audit, with file edits you can undo.

The ask

One team. One workflow. Four weeks. Fund a pilot that measures ticket-to-PR time, not message volume.

01 · The landscape

Three tools, three layers

These are not three versions of the same product. Each owns a different part of the work. The gap is between the systems that know what happened and the repo where it gets fixed.

The read layer

One-Search

One place to ask what is happening across Jira, GitHub, Datadog, and the rest. A service account gives it breadth. It is read-only by design.

Strong at: org-wide retrieval.
Stops at: action.
The edit layer

VS Code + Copilot

The editor where developers already read and change code. Fast for one file, one developer, one open workspace.

Strong at: the file in front of you.
Stops at: the editor boundary.
The action layer

Fid Coder

A local agent with its own workspace, tools, memory, schedule, and approval gate. It reads the systems, acts in the repo, and proves the result.

Strong at: closing the loop.
Stops at: the approval gate.

02 · What stands out

The loop, the brake, the receipt

The differentiation is not a longer feature list. It is the shape of the work: a cross-system question becomes a verified change, and the change is visible and reversible.

Loop

It closes the loop.

One-Search can tell you a ticket is failing. VS Code can change the file. Fid Coder can do both in one turn: read the ticket, find the code, patch it, run the test, and show the diff. The turn does not end at a suggestion.

jira_issue search_text apply_patch shell_run git_diff
Context

The context crosses the boundary.

One agent turn can combine Jira, a GitHub pull request, the local repo, and a logged-in browser page. Ask mode keeps the question read-only by removing the write tools. Agent mode adds the edit and run tools. The project map and path:line citations make the reasoning inspectable.

Ask mode project map path:line citations code reader
Brake

Autonomy has a brake and a receipt.

Deletes, pushes, and downloads stop at an approval card that names the command, folder, and reason. Allow once, always allow, reject, or always deny. Deny wins, and every decision lands in the audit history. File edits are checkpointed with a diff and a one-click revert.

approval card saved rules audit history checkpoint + revert
Identity

It runs on the user's identity, not a shared service account.

Jira and GitHub tokens are personal and encrypted with Windows safeStorage. The browser uses a per-agent profile with the user's existing login. There is no new admin grant and no broad shared credential. The activity is attributable to the person at the PC.

safeStorage per-agent browser profile personal PAT
Cadence

It becomes a scheduled teammate.

Routines run a saved instruction on a cron schedule and raise a Windows toast. Memory carries context across sessions. Skills encode a team's review or triage playbook and can live in the repo. The Agent Desk shows the browser preview, approvals, routines, changes, and diffs while the work happens.

03 · The proof

A five-minute demo

Show the loop once, end to end. Do not open with a feature tour. Open with a ticket that a manager already recognizes, and let the agent carry it to a test run and a diff.

  1. 01

    Ask the question in Ask mode.

    “What does this bug touch?” The agent reads the Jira issue, searches the repo, and answers with path:line citations. Choose a citation to open the code reader with the exact range highlighted.

  2. 02

    Switch to Agent mode and fix it.

    “Fix it and run the failing test.” Watch the tool card step through the patch and the test run. The Agent Desk shows the change set and the diff without opening a terminal.

  3. 03

    Show the brake.

    Ask for a push or a delete. The approval card names the command, folder, and reason. Choose Reject to show the deny path and the audit entry. Explain that allow once or a saved rule is the normal path.

  4. 04

    Show the receipt.

    Open the diff and revert the file. The workspace is restored. Point out that this works for file_write and apply_patch; shell-made file changes are not checkpointed.

  5. 05

    Show the cadence.

    Open a weekday 9:00 routine and its last status. Say the limit plainly: routines run while the app is open; tray and keep-running are the next step. Close on the loop, not the schedule.

Set up before the demo

A sample repo with one failing test, a Jira issue that points at it, Copilot signed in, and a developer agent with that workspace. Save the Jira PAT first. Do not open Datadog SSO in the first demo; it is a separate, unproven dependency.

04 · The pilot

What leadership gets

A four-week pilot with a baseline week and a clear stop rule. The point is to measure the loop, not adoption of another chat window.

Success bar
20% faster from ticket to first reviewable PR
or
30 min saved per developer per day

One team, one workflow, four weeks. If it misses, stop and report. Do not expand.

Guardrail

Zero unapproved destructive commands. Every approval decision auditable. Every file edit made through the file tools is reversible.

Pair the pilot with a security review of secrets, browser profiles, and the audit export. That review is part of the deliverable, not a later gate.

05 · The honest part

Risks and answers

The fastest way to lose the room is to overclaim. These are the objections leadership will hear, with the truthful answer and the next move.

Common objections to Fid Coder, the truthful answer, and the recommended next move.
Objection The truthful answer The next move
“One-Search already covers the read.” It does. It cannot act. Rebuilding its connectors would duplicate the team's work. Make One-Search a read tool in Fid Coder. Use its breadth as the top of the funnel.
“VS Code already does coding.” It should stay the editor. Fid Coder is the cross-system desk with a schedule and an audit. Position it as a complement. Do not build an IDE.
“This is a per-PC tool, not a team platform.” True today. Agents, transcripts, and audit are local. Skills can live in the repo. Share playbooks as repo skills. Ship threads and an audit export before an org rollout.
“Routines stop when the app closes.” True. The scheduled-worker story is not unattended yet. Ship tray, keep-running, run history, and an inbox before claiming unattended work.
“Shell access is risky.” Deletes, pushes, and downloads pause for approval. Other commands run without a prompt, and shell-made file changes are not checkpointed. Extend the gate to remote writes such as PR creation and issue updates. Add policy templates. Keep deny-by-default for new tool classes.
“Is Datadog covered?” It is a draft. SSO inside the automated browser is unproven. Test SSO first. If blocked, use One-Search for Datadog and keep Fid Coder on Jira, GitHub, and the repo.
“How does it get installed and paid for?” A portable Windows build exists. Corporate allowlisting is still a dependency. Every turn spends Copilot credits. Get one approved internal distribution path. Track credits per merged change in the pilot.
06 · The plan

Three moves, one non-goal list

The strategy is integration, not a feature race. Fid Coder should own the action loop and consume the read layer that already exists.

Move 1 · Highest leverage

Integrate One-Search.

Add a read-only One-Search tool or MCP client. Fid Coder keeps the action loop; One-Search supplies the cross-system read. This turns a parallel effort into the top of one funnel.

Move 2 · Make it legible

Ship threads, then routines 2.0.

Threads separate routine, ticket, and review work. Tray, run history, and an inbox make the scheduled-worker story real. Add an approval audit export for security.

Move 3 · Package the loop

Productize ticket to verified change.

A built-in skill and starter prompt for the hero workflow, plus a weekly outcome digest routine. Use what already exists; add no new architecture.

Do not build
  • A connector catalog to match One-Search.
  • An IDE or inline editing.
  • A server or multi-tenant control plane before the local pilot proves value.
  • Unattended scheduling claims before the tray ships.
  • More integrations before threads and routines are legible.

One-Search tells you what happened. VS Code lets you change the code. Fid Coder is the only one of the three that can take what happened, change the code, run the test, and hand you the receipt.
