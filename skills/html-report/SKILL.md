# Make an HTML report

Use this skill when the user asks for a brief, memo, one-pager, comparison, status page, incident review, or a designed page for other people. The output is one standalone HTML file they can open, print, or share.

Do not use it for a normal chat answer, a code review (`/review`), or a report that should stay in the conversation. Do not make a report for every question.

## Before you write

This skill needs a workspace and `file_write`. If the agent is in Ask mode or has no workspace, say so and ask the user to switch to Agent mode or pick a workspace. Do not paste the HTML into chat as a substitute.

Read `template.html` with `skill_read` first. On a later message, pass `skill="html-report"` and use `limit: 400`. Use the template's CSS and structure. Replace every `[Replace: ...]` marker. Delete sections you do not need. Do not invent a new visual system or add a CSS framework.

## Choose the shape

Pick 3 to 6 sections. Start with the decision, not the background.

- Leadership brief: hero, three cards, comparison table, risks, next steps, sources.
- Status report: hero, metrics, what shipped, what is next, blockers, sources.
- Incident review: hero, impact metrics, timeline, root cause, what changed, open risks, sources.
- Comparison: hero, comparison table, three cards, risks, recommendation, sources.
- Architecture explainer: hero, component cards, flow steps, boundaries, risks, reading order, sources.

A hero has a headline, a one-sentence dek, and an ask. A section has an eyebrow label, a heading, and at most three short paragraphs. Use a table when the reader must compare. Use cards for 2 to 4 parallel items. Use steps for a real sequence. Use a callout for one decision or warning.

## Write for the reader

- Put the answer in the first two sentences. The reader may stop there.
- Use short sentences and concrete nouns. Name the decision, the evidence, and the ask.
- Every number needs a source from a tool result or the user. If you do not have one, leave the number out.
- Cite code as `path:line`. Cite Jira keys and PR numbers as text.
- Separate facts from recommendations. Put assumptions in a callout or a risks row.
- End with the ask or the next decision, not a feature list.
- No marketing adjectives, no filler, no "in today's fast-paced world".

## Fill the template

1. Page title: 2 to 5 words. Use `reports/<slug>-<YYYY-MM-DD>.html` unless the user names a path.
2. Masthead: report type, audience, and date.
3. Hero: headline, dek, ask.
4. Sections: 3 to 6. Delete unused sections; leave the CSS in place.
5. Sources: every file, ticket, PR, or page you used.
6. Footer: keep "Generated by Fid Coder. Review before sharing."

Write with `file_write`; it creates parent folders and checkpoints the file. For a revision, use `apply_patch` and change only the content, keeping the CSS and structure. After writing, report the path and a two-line summary. Do not paste the HTML into chat.

## Safety

- Escape `&`, `<`, and `>` in every value that came from a tool, a user, or a file.
- No `<script>`, `<iframe>`, `<object>`, `<embed>`, inline event handlers, external stylesheets, external fonts, external images, or network calls.
- Do not embed tokens or secrets. Redact values that look like `ghp_`, `github_pat_`, `ATATT`, `xoxb-`, or a long random string.
- Do not include a Mermaid block. A standalone file has no renderer. Use a table or the numbered steps block; the chat can render Mermaid separately.
- Keep the CSP meta tag from the template.
- Keep the footer warning. The reader must review the page before sharing it.

## Check before you finish

- The page opens as one file with no external requests.
- Every `[Replace: ...]` marker is gone.
- Every number has a source, and every code claim has `path:line`.
- The title and headings say what the page is for.
- The file is inside the workspace and the path is reported.
